# Bare-metal EPYC 7513 replication

Status: Linux ELF64 linking is repaired and the paper's speculative AES/RSA
success cases reproduce on this host. A rare Write-Execute first-result error
also reproduces on bare metal and remains unresolved. Do not infer native
Write-Execute reliability from the passing deterministic suite.

Recorded 2026-10-19 on a two-socket AMD EPYC 7513 (Zen 3, family 19h model
01h) host running Rocky Linux 9.8 and kernel 5.14.0-687.36.1.el9_8.x86_64.
The reported microcode revision was `0xa0011d5`.
The original checkout was commit `8037793`. Builds and runs used a 1.5 GB
`systemd-run --user --scope -p MemoryMax=1500M` limit and one test process at
a time. `RDTSCP`, `CLFLUSH`, SSE2, and AES-NI were present. CPU 0 and CPU 33
are on different sockets. This host is bare metal, not the virtualized Windows
EPYC 7763 runner where earlier transient arithmetic errors were observed.

## Linux x64 assembly failure and repair

The unmodified checkout built successfully with pinned UASM 2.57, but CTest's
`edge_vectors` and `writeexec_harness` both segfaulted. GDB caught the first
fault at `shlres` (linked address `0x416175`), with `si_addr=0x26416181`.
The text segment was already `rwxp`; page protection was not the cause.

UASM's ELF64 `.rela.text` contained nonzero instruction displacement fields
*and* explicit addends for `R_X86_64_PC32` relocations. In this link,
`mov [shlres+3], ...` actually targeted `shlres+6`, and the other two wrapper
stores targeting `shlarg+2` and `shlret+1` landed at `+4` and `+2`.
After zeroing the in-place PC32 fields in the generated object, `objdump`
showed all three stores at their intended instruction bytes. The build now
performs this normalization between UASM and the ELF link. The first object
had 479,855 PC32 fields to normalize; the RSA object had 18 nonzero fields
among 62 PC32 relocations. ELF32 uses implicit REL addends and is untouched.
The [x86-64 psABI](https://gitlab.com/x86-psABIs/x86-64-ABI/) specifies the
`R_X86_64_PC32` result as `S + A - P`.

With manually normalized objects, all four CTest cases passed. A second,
fresh build through the new CMake rule also normalized both objects and passed
all four cases (`edge_vectors` 61.95 seconds, `writeexec_harness` 56.68
seconds). The correction is a Linux/macOS assembler-object transformation;
it changes the linked displacement bytes to the source's intended targets,
without changing the Write-Execute algorithm or the Lean model.

On the final no-fence image, the `.text` SHA256 was
`543fb23228f0d0a1d9bb80fd791b8346c2c771504e272d9e53c32f3de64a5b59`,
identical to the earlier diagnostic image after exporting symbols. A later
CTest run on this image passed three of four tests. `edge_vectors` recorded
four transient failures among 232,085 vectors: one MUL32, two DIV32, and one
MODEXP32. Each immediate repeat returned the reference result, and the
logged CPU number remained 66 during each failure and retry. The same
relocation repair therefore removes the deterministic segfault but does not
remove the separate intermittent native error.
A follow-up `taskset -c 0` run of `edge_vectors` failed three of 232,085
vectors: one DIV32 and two MOD32. Each immediate repeat passed on CPU 0.
CPU pinning alone therefore does not remove the error.

## Speculative AES and RSA

On CPU 0, automatic AES timing calibration reported hot p90=78, cold p10=260,
full-sweep cold p01=234 cycles, and selected a threshold of 156. The four
AES modes returned:

| AES mode | CPU 0 correct / confident | CPU 33 correct / confident |
| --- | ---: | ---: |
| Ten rounds, C | 0/10 / 0/10 | 0/10 / 0/10 |
| Ten rounds, AES-NI | 10/10 / 10/10 | 10/10 / 10/10 |
| One round, C | 0/10 / 0/10 | 0/10 / 0/10 |
| One round, AES-NI | 10/10 / 10/10 | 10/10 / 10/10 |

The final linked image repeated the same 0/10, 10/10, 0/10, 10/10 mode
results on CPU 33.

The first Linux RSA depth sweep returned zero correct at every tested depth,
including one multiplication. GDB then read the intended `input=1` location
at the first speculative victim call and found `0xd9bc34e0`. The local C
object's address had been converted to an integer, but the optimizer had no
reason to keep its value live through the call. Making the depth input
`volatile`, reading it after the call, and doing address subtraction with
`uintptr_t` caused the same GDB probe to read `0x00000001`. The full-chain
intermediate input now has the same explicit lifetime and integer address
calculation. The existing `__cdecl` declaration intentionally uses the
Microsoft x64 ABI for the assembly entry points on Unix; their original
RCX/RDX register convention is correct.

After that fix, CPU 0 and CPU 33 each returned 10/10 correct and confident
for every direct one-, two-, four-, five-, six-, and eight-step case, C and
assembly where available. The complete chained RSA program returned 160/160
correct and confident groups on each CPU, including a rerun with the final
extended-sweep source on CPU 0. The final linked image repeated the full
depth sweep at 10/10 in all eleven modes on CPU 33. Thus the measured boundary
on this EPYC is
beyond eight modular multiplications; the experiment does not locate its
upper limit. The current Intel i9-14900HX x64 and x86 builds also returned
10/10 correct and confident in all eleven direct modes through eight steps.
CPU 32 and its SMT sibling CPU 96 rejected
the RSA preflight because most flushed probe lines were classified as hits;
the separate CPU 33 on that socket passed preflight and all tested depths.

Reproduce the focused checks after a Release CMake build with:

```sh
taskset -c 0 build/amd111/edge_vectors shr32 20000000 0x91c5c554
taskset -c 0 build/amd111/edge_vectors shr32pair 1000000 0x91c5c554
taskset -c 33 build/amd111/edge_vectors shr32pair 1000000 0x91c5c554
taskset -c 0 ctest --test-dir build/amd111 -R edge_vectors --output-on-failure
WE_CPU=0 build/amd111/selfspectre_aes
WE_CPU=0 build/amd111/selfspectre_rsa --depth-sweep
WE_CPU=33 build/amd111/selfspectre_rsa --depth-sweep
```

`build/amd111` is the local build directory name. Run one process at a time
under the stated memory cap when repeating the full suite.

## Remaining native arithmetic anomaly

The separate Debug x64 Windows access violation was already explained by an
incremental-link thunk and fixed by disabling incremental linking. The rare
first-result arithmetic errors remained open. This bare-metal host reproduced
that class of failure with CPU 0 pinned:

| Focused SHR32 run | First bad call | Observed | Expected | Immediate repeats |
| --- | ---: | ---: | ---: | ---: |
| seed `0x91c5c554` | 356,515: `0x30b64536 >> 3` | `0x0616c8a0` | `0x0616c8a6` | both expected |
| same seed, instrumented rerun | 260,918: `0x1f7d25b7 >> 22` | `0x00007d7d` | `0x0000007d` | both expected |

Both mismatches occurred on logical CPU 0 without migration. In the second,
the entry, split, lane, and index patch bytes read back as 22, 192, 6, and 6.
This rules out Windows or virtualization being *necessary* for the transient
class.

A paired-call run on CPU 0 used one million changing inputs and called
`WriteExecSHR32_C` twice with identical operands for each input. Three first
results were wrong; all one million immediate second results were correct.
The same sequence on CPU 33, on the other socket, produced four wrong first
results and no wrong second results.
The diagnostic confirms an intermittent first-call failure under repeated
input changes, while identical immediate retries mask it. It is not a
correctness guarantee on the first call.
The same one-million-input sequence produced zero wrong first or second
results in a local Windows x64 run on the i9-14900HX. That comparison is a
finite negative sample; the local run did not pin a logical CPU.

After exporting intermediate instruction labels for diagnostics (without
changing executable bytes), repeated pinned SHR32 failures showed that the
final result used the low three shift bits from the immediately preceding
call. For example,
`0x66f9267e >> 27` returned `0x19` (the result for shift 26) instead of
`0x0c`. Its entry byte was 27; `shrrounds`'s immediate was 3, but the
subsequent dispatch and low-bit source both held 2. The result bytes had
already been patched to `0x19`, so this was not a stale return load.
`shrrounds` transfers a split output to the dispatch; no other SHR32
instruction writes that dispatch after it. The final bytes establish a stale
low-bit *handoff*, but cannot by themselves distinguish a stale decoded
`shrrounds` instruction, a missed execution of that instruction, or an
earlier stale stage. The first split-output byte is overwritten by the second
split during the same call, so its final value is not a record of the first
execution. The failure is in same-thread self-modifying instruction
sequencing, not the arithmetic formula or cache-based measurement. This
diagnoses the observed path without claiming that every rare failure has the
same site.

The controlled follow-up inserted a three-byte `MFENCE` after the shared SHL
byte-result stores. Its x64 RIP-relative patch formulas were adjusted to the
new return-label position; without that adjustment the experiment was
deterministically broken. Three equal-length linked variants, differing only
in those three instruction bytes, then produced their first wrong `SHR32`
result at call 937,732 (`MFENCE`), 34,084 (short jump plus NOP), and 128,336
(three NOPs) under the same seed and CPU pin. Every variant failed. These
single first-failure samples do not establish a rate difference. The fence
failure had the current shift count in the post-call dispatch and low-bit
fields but a wrong patched result byte, so the failure was not confined to
the SHL handoff targeted by this fence. The fence
was removed from the source. [AMD's APM](https://docs.amd.com/v/u/en-US/24593_3.44_APM_Vol2)
describes `MFENCE` as serializing on AMD64 and says same-thread modified
instructions are automatically refetched. Intel recommends a jump or a
serializing instruction for same-thread self-modifying code, but does not
make the same `MFENCE` promise. The observed result shows that this one
handoff is not the whole failure path. Neither the matched experiment nor
AMD's page-remapping erratum establishes a processor defect.

A separate test placed a serializing `CPUID` before each call from the C
diagnostic harness, leaving the Write-Execute assembly unchanged. With
three million paired inputs on CPU 0, nine first results were wrong and all
immediate second results were correct. A variant that serialized only the
first call also produced a wrong second result at input 500,976. An
entry-side serialization step is therefore insufficient; these experiments
do not establish which internal patch-to-execute transition fails. The
temporary CPUID harness option was removed.

GDB 16.3 on the bare-metal EPYC also stopped an optimized, symbol-bearing
`edge_vectors` binary at the first C mismatch, before either diagnostic retry.
The optimized `main` machine code was byte-identical to the normal harness;
the breakpoint was outside the hot assembly. Three independent pinned CPU 0
runs with seed `0x91c5c554` stopped at inputs 95,457, 161,737, and 456,780.
Their respective results were `0xb7edd1ee >> 0` for a requested shift of 1,
`0xbd1b2ff0 >> 8` for 9, and `0x9f433fe3 >> 11` for 12. In all three,
the entry instruction's immediate held the requested shift, while the
low-bit source and final result bytes reflected the smaller shift. The
shared SHL return-store instructions still targeted the intended SHR32
sites, and the process had one thread with writable/executable text. This
localizes the visible error to a patched-code handoff before the final
result. A post-call snapshot cannot identify the first stale execution,
because the shared SHL path rewrites some of those sites again within one
call. GDB branch tracing was unavailable: the host reported BTS disabled.

A further controlled test inserted `MFENCE` between the last patch in
`WriteExecSHR32_C` and its jump to `WriteExecSHR32`. The matched NOP image
was made by replacing only those three fence bytes in the same assembled
object. Their linked `.text` sections differed by exactly three bytes.
Pinned to CPU 0 with the same seed, the fence image first failed at input
64,803 (`0xb3762359 >> 3` returned the shift-two result); the NOP image
first failed at input 469,747 (`0xcf76d47d >> 19` returned the shift-18
result). Both immediate retries passed. Thus fencing this wrapper boundary
does not repair SHR32, and these two first-failure samples do not support
a rate comparison. This fence was not added to the published source.

Copied x64 ELF images then routed selected jumps through unused NOP padding.
Each controlled pair used identical branches and layout; one trampoline
executed `push rbx; xor eax,eax; cpuid; pop rbx`, the other six NOPs. Each
line below is the first bad call in a pinned CPU 0 run with three million
maximum inputs and the same seed. All failures corrected on immediate retry.

| Serialized transition | CPUID first failure | NOP first failure |
| --- | ---: | ---: |
| SHR32 wrapper to entry | 100,836 | 16,782 |
| Both SHR32 split-stage jumps | 191,861 | 1,033,145 |
| Shared SHL5 and SHL6 dispatches | 2,440,992 | 594,793 |
| All four preceding internal dispatches together | 133,401 | 224,107 |
| All 2,048 linked SHL table jumps to `shlbres` | 1,791,074 | 138,549 |
| Wrapper, four internal dispatches, and SHL table returns together | 1,993,284 | 230,530 |

The ELF `.text` comparison for each pair differed only in the six CPUID
trampoline bytes per site. These probes show that even architecturally
serializing `CPUID` at these selected groups, even together, is insufficient;
they do not identify the earliest failing patch-to-execute transition.
The combined variant's failure had the correct low shift bits but one wrong
interior result byte. SHR32 subsequently calls the shared SHR and XOR paths
for each byte; this snapshot does not identify which of those later paths
first diverged.
The probes were made only in ignored diagnostic binaries.
Serializing every handoff would also change the speculative execution path,
so these probes are not a replacement for the paper's working AES/RSA code.

The baseline assembly object was also relinked after inserting 16, 32, 48,
or 64 NOP bytes before it, moving `WriteExecSHL` from 64-byte-line offset 60
to offsets 12, 28, 44, and 60 respectively. The 16-byte layout passed one
three-million-input SHR32 run but failed a subsequent run at input 301,907.
The other layouts failed by input 945,003, 28,078, and 200,779 respectively.
Failure timing varied with placement, but none was reliable. Moving the one
observed crossing instruction off a cache-line boundary does not fix the
anomaly. No placement change was retained in the source.

To test Linux text-page copy-on-write directly, a diagnostic copy of the
edge-vector harness wrote each assembly page's first byte back to itself
after `mprotect` and before any vector. It materialized 3,765 pages. The
same diagnostic binary passed ten million focused SHR32 inputs with and
without this pre-touch, so those two passes do not isolate its effect.
The full pre-touched suite then had a transient DIV32 failure in one of
three runs (232,085 vectors each); the other two passed. Thus a first-write
copy-on-write transition is not necessary for the bare-metal anomaly. The
ordinary restored baseline suite failed in each of three separate control
runs, but its linked layout differs from the diagnostic binary, so those
counts do not establish a pre-touch rate change. The Windows pre-private
CI hunt had also failed after all assembly pages were materialized.

The 29 internal jumps did not eliminate this anomaly; their independent
portable sequencing role has not been disproved. Existing table padding is
part of the original machine-code design, not a confirmed remedy for this
transient.

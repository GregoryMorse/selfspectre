# Validation tooling

- `limited_run.py` — runs a command under a 1.5 GB aggregate memory cap (Windows Job Object). Always use it.
- `build_modules.py` — guarded module-by-module Lean build (Lake exceeds the cap). Mathlib modules are CI-only.
- `axiom_audit.py` — checks locally buildable `WriteExecute` declarations use only the three standard axioms.
- `native.py` — builds/runs the legacy `writeexec` harness in the four configurations (`vs/` projects, output in `build/msbuild`).
- `cmake_local.py [x86|x64]` — local MSVC build and ctest of the CMake targets (`build/msvc-<arch>`); `msbuild_local.py [Config|Platform ...]` — builds `vs/selfspectre.sln` (output in `build/msbuild`). The portable grid (Windows, Linux x86/x64, macOS x64) runs in `.github/workflows/portable.yml`.
- `build_native_demos.py [x64|x86]` — focused MSVC Release build of the AES and RSA demos plus deterministic C vectors in `build/native/<arch>/Release`; it does not build `spectrepoc`. It selects RDTSCP or the RDTSC+LFENCE fallback from CPUID (`WE_FORCE_RDTSC=1` exercises the latter). Run it through `limited_run.py`. `build_cache_timing.py` builds the isolated 512/4096-byte timing diagnostic into `validation/.build`.
- `SPECTRE_INVESTIGATION.md` — current-machine diagnosis, repair, and guarded AES/RSA results. The speculative demos are hardware measurements and are not part of CTest.
- Listings (needed by `extract_layout.py`/`purity_scan.py`): copy `src/writeexc.asm` and `asm_listings.bat` into
  `validation/.build/lst/`, run `asm_listings.bat` there (x86 + x64 listings, ~170 MB each, never committed),
  then `python validation/extract_layout.py` and `python validation/purity_scan.py`.
- `layout/{x86,x64}.json`, `layout/purity.json` — committed outputs.
- `reference/` — published TMMP PDF (SHA-256 `8d9b4072…1940`) and its `pdftotext -layout` text.
- `run_listings.py <name> [asm]` — assembles a copy of `src/writeexc.asm` (x86 + x64, with listings) into `validation/.build/<name>/`.
  `lst` = the published source (git history before L04), `lstc` = the current corrected source.
  `extract_layout.py [lst|lstc]` writes `layout/{x86,x64}.json` (published) or `layout/{x86c,x64c}.json` (corrected);
  `gen_x86_layout.py` turns all four into `lean/WriteExecute/X86/LayoutData.lean`.
- `compare_listings.py` + `compare_dump.lean` — evidence: the bytes the Lean byte model assigns to the NOT/NZ/SHL4 table entries
  and fixed instructions equal the relocated COFF `.text` (needs the four objects and built oleans).
- `make_challenge.py [--check]` — generates `lean/Challenge.lean` from the Spec modules (plan D6).
- `palomar/` — pinned policy assets (`refresh_policy.py`, `fetch_policy_assets.py`) and `validate_metadata.py`
  (`lean/formalization.yaml` against the pinned v0.4 schema and the registry taxonomies).
- `ci/` — `linux.sh` (cold build, Challenge/Solution, `axioms.py`, generated-file and errata checks) used by `.github/workflows/proof.yml`.
- `native_edge.py` — assembles `src/writeexc.asm` (x86, x64) and runs `native/edge_vectors.c`: deterministic boundary vectors (232,085 checks: all 8-bit pairs, every shift count, carry/borrow boundaries, MUL32/DIV32/MOD32/MODEXP32, four captured CI triples, FIPS-197 C.1) against the assembled entry points. Evidence, not proof.
- `edge_vectors modexp N [seed]` — focused assembled `MODEXP32` versus an independent 64-bit C reference for the captured Debug|x64 CI triple followed by `N-1` random triples; prints the seed and exact operands on the first failure and fails even if immediate repeats pass. The seed-to-sequence mapping is preserved for hosted replay. The ordinary edge run separately includes all four captured CI triples. The Windows CMake suite runs 100 focused calls per job.
- `edge_vectors shr32 N [seed]` — focused assembled `SHR32` sequence that keeps one input across 32 successive shift counts; on the first mismatch it prints the input, count, preceding expected result, patched entry count byte on Windows, intermediate split and lane bytes on x64 Windows, repeats, and guest logical CPUs. The manual Windows hunt runs 320,000 calls per job.
- `edge_vectors mul32 N [seed]` — focused assembled `MUL32` differential sequence. On a mismatch it prints both operands, the first result, two repeats, and the shared `SHR32` count byte on Windows. The manual Windows hunt runs 20,000 calls per job to investigate doubled results seen in the legacy harness.
- The ordinary edge-vector MODEXP32 checks also print exact operands on a mismatch. `WE_PIN=1` makes the harness fail explicitly if affinity cannot be set. `WE_PREPRIVATE=1` is a Windows-only diagnostic that writes back each assembled-code page's first byte before testing and verifies that the page becomes `PAGE_EXECUTE_READWRITE`; it removes first-write image-page copy-on-write transitions from the measured calls without changing the Write-Execute procedures.
- `patch_alignment.py <writeexc.obj> <edge_vectors.map>` — resolves simple byte/word/dword code-patch sites against the *linked* MSVC image and reports stores that span a 64-byte cache line. The Windows CMake harnesses emit linker maps and CI prints this diagnostic. Object-file offsets alone are insufficient because the linker shifts the assembly section relative to the cache-line grid.
- `listing_patch_alignment.py <writeexc.lst> <writeexc.obj> <edge_vectors.map>` — audits the macro-expanded MASM listing, checks that its `DIV32_C` address matches the object, and resolves every matched byte/word/dword `mov` store target against the linked image. Generate listings with `run_listings.py` under `limited_run.py`. This is a deeper local diagnostic; the large listings are not committed.
- `audit_smc_fallthrough.py` — checks that a straight-line assembly block does not store into a labeled instruction and then fall through to that label. This is a source check of one self-modifying-code sequencing rule, not a proof of runtime behavior.
- `native_vectors.py` — exact Python-generated vectors for the corrected C `mulmod`/`fastmodexp`/`modexp` (L02, L03).

## Rare native mismatches (open: reproduced)

Four times in CI, on GitHub `windows-2022` runners, a native check returned a wrong result once and a repeat passed. One was
an assembled Write-Execute call: `edge_vectors` Win32 `DIV32` ("got 1fe want 1fe": the first call was wrong, the immediate
repeat right). The other three were in the **plain-C first block** of the legacy `writeexec` harness on x64 (one wrong 32-bit
value, or a burst of seven). That block ends before the first `WriteExec*` call in `src/writeexec.c`, so those three events
cannot be attributed to a stale fetch inside the Write-Execute assembly during the failing check. Each subsequent attempt
passed. The two classes of event may have different causes.

A fifth event occurred on 2026-10-18 in the `writeexec` Debug|Win32 `WriteExecMODEXP32_C` check at
`src/writeexec.c:822`: `0D2366D8` versus C reference `11E52FFA`. The old check recorded neither
inputs nor same-input repeats. Passing other configurations with fresh random inputs does not show
whether this was transient or input-specific. The check now records inputs and repeats the same
assembled call twice on mismatch. Two matching repeats are labelled `transient`; every wrong first
result now fails `validation/native.py` and CTest.

A sixth event occurred on 2026-10-18 in the push-triggered [proof/native run #46](https://github.com/GregoryMorse/selfspectre/actions/runs/39151226301), `writeexec` Debug|x64 `WriteExecMODEXP32_C` at `src/writeexec.c:833`. For base `2997D078`, exponent `4C815A47`, modulus `2A94AE94`, the first call returned `122C3628` instead of `1D3A89A8`; two immediate same-input repeats returned `1D3A89A8` on CPU 0. The independent modular-exponentiation reference also returns `1D3A89A8`. This event occurred after the earlier alignment changes and disproves closure based on the prior negative stress runs.

The [60-job Windows hunt #7](https://github.com/GregoryMorse/selfspectre/actions/runs/39156169406) on `e2db238` (with the 29 new jumps) found **five more first-call MODEXP32 mismatches**: three Win32 and two x64. Two reported different logical CPUs between the first result and repeats; three reported the same CPU. All five ran on virtualized AMD EPYC 7763 Windows Server 2022 hosts, and all immediate same-input repeats were correct. The failures occurred in the legacy harness, focused random MODEXP32 loop, and deterministic edge vectors. The two failing focused seeds were `0x03271bd0` (iteration 94) and `0xf4e530c5` (iteration 87); replaying the generator produces the exact logged operands at those iterations. Thus the jump addition did not eliminate the anomaly, and migration alone is not established as its cause. The deterministic edge-vector checks previously printed `B[i] B[j] M[k]` literally; they now print their operand values.

For the iteration-94 triple, the wrong `1fe2f734` equals the independent reference result with exponent bit 31 cleared (`ff9bd8cd` → `7f9bd8cd`), or equivalently the accumulator after bit 30. This narrows that event to a possible missed final exponent step; it does not identify the faulty instruction or establish a CPU cause. The other captured MODEXP32 wrong values do not equal the result of flipping any single input bit.

What was established:

- `ref_soak` found no mismatch in 150 million random iterations on each of 32 runners or 100 million locally. It copies the
  plain-C functions but uses nonzero odd divisors, its own random generator and a separate binary; this negative result does
  not rule out a first-block C, optimizer or input-dependent cause in `writeexec`.
- The first block's expected signed remainder formerly contained `((int64_t)num1 << 32 | num2)`:
  for `num1 >= 0x80000000`, that C expression has undefined behavior. The signed multiplication
  and division helpers also negated the minimum signed values. These reference defects are repaired
  in both the legacy harness and `ref_soak`; none is proven to have caused an observed CI event.
- The assembled `edge_vectors` case is not input dependent in the usual deterministic sense: it uses fixed tables and its
  repeat call was right. The three plain-C legacy events used random inputs.
- At least one earlier event occurred with the thread pinned (`WE_PIN=1`), so migration alone cannot explain all events.
- For the one assembled `DIV32` event, an immediate repeat call was right, but that does not isolate which code patch or fetch failed.
- The first four events were not reproduced in 26 local runs, 80 + 32 + 32 runner runs of the instrumented harnesses, or in 120 later runner runs (the later
  runs also carry a changed `writeexec.c`, so the code layout differs). They were sparse enough that layout or
  platform effects cannot be separated statistically with a reasonable number of runs. Linux and macOS runners have been run
  far fewer times (about 15 each), so the absence of events there is not evidence of a Windows-only effect.
- The five hunt failures establish a concrete affected environment, virtualized AMD EPYC 7763 with Windows Server 2022; they do not establish that this CPU model or Windows version alone is the cause. Other tested runners include AMD EPYC 9V45/9V74 and Intel Xeon 8370C/8573C/6973P-C.

The source audit after that event found 29 straight-line paths in `src/writeexc.asm` where a store patched an instruction later executed by fallthrough. Intel SDM Vol. 3A §10.1.3 recommends a jump to the new or intermediate code, or a serializing instruction, for portable same-thread self-modifying code; the existing wrapper jumps did not cover these internal paths. Each path now branches to its first patched instruction, and `audit_smc_fallthrough.py` guards the source pattern in CI. The regenerated x86 and x64 MASM listings encode all 29 new branches as `EB 00` (a jump to the immediately following instruction); Intel does not specifically say whether this zero-displacement form provides the recommended sequencing on every microarchitecture. The corrected layout JSON and Lean layout constants include the resulting 16-byte shift of the Fig. 7 carry labels. The affected Lean modules build, and `compare_listings.py` reports 7,778 byte strings matching the current objects.

The added branches address the audited source pattern, but are not an explanation of the AMD hunt failures or the earlier `DIV32` event. AMD APM Vol. 2 §7.6.1 explicitly says its processors detect in-flight self-modification, flush and refetch, with no special software action. Intel's `MACHINE_CLEARS.SMC` performance event counts detected SMC that causes a pipeline clear; it does not report that every code store needs one, and it has not been measured on the failing AMD VM. Neither manual imposes a half-page correctness restriction. The machine clear is a hardware recovery path, while Intel's store-then-jump or store-then-serialize sequence is source-level portability guidance. `native.py` now records the host CPU and Windows version for future correlations. `edge_vectors` and the focused `edge_vectors modexp N seed` mode record the first wrong result,
exact operands in the focused mode, and two same-input repeats. Any wrong first result now fails the run, even if the
repeats pass; CI no longer retries the Windows CTest step. Mismatch lines in the legacy harness carry their source line
and CPU. [Intel SDM Vol. 3A](https://cdrdv2-public.intel.com/835754/253668-sdm-vol-3a.pdf);
[Intel `MACHINE_CLEARS.SMC` event](https://perfmon-events.intel.com/platforms/emeraldrapids/core-events/core/);
[AMD APM Vol. 2](https://docs.amd.com/v/u/en-US/24593_3.44_APM_Vol2).
`.github/workflows/flake-hunt.yml` (manual) repeats the tests on many runners. This is native evidence only and does not enter any
Lean statement.

Follow-up alignment audit (2026-10-18): the local linked `edge_vectors` images had 12 (x86) and 10 (x64) statically resolved 32-bit patch fields that span a 64-byte line. Some occur in helpers reached by division (for example x86 `shr32arg1_3+2`, x64 `xorret+1` and `divshl1loop+1`). The initially suspected `divres4+2` crossing in the x86 *object* did **not** cross in the linked vector binary. Relinked x86 and x64 vector binaries each passed 232,081 checks with zero transients. A crossing is a measured layout fact, not evidence that it caused a mismatch. The diagnostic does not turn a crossing into a failure; eliminating one crossing would shift other code and could create another elsewhere. A fix requires a controlled linked-layout comparison with enough repeated calls to distinguish it from the observed low event rate.

The CMake CI link before the jumps (`69861af`) had 12 crossing patch fields on Win32 and 10 on x64. The link after the jumps (`e2db238`) had 15 on Win32 and 17 on x64; among the later crossings are `div32arg1_6+2` and `div32rem2_3+2` in the shared division path. The number of patch sites remained 696 and 689, respectively. This is a layout change worth testing, not evidence of a torn fetch: the five failures came from separate hunt binaries whose linked offsets were not captured, and the two CI versions were not compared on matched hosts. The manual hunt workflow now records the linked layout, replays both failing focused seeds, and accepts a `pin` input to prevent *guest logical-CPU* migration and a `preprivate` input to pre-materialize the code pages. The hypervisor can still move a vCPU between physical cores.

A local x64 probe of the linked executable found nine nearby assembled-code pages initially mapped as shared `PAGE_EXECUTE_WRITECOPY` image pages. After a single MODEXP32 call, five pages that the computation wrote were private `PAGE_EXECUTE_READWRITE` pages; the call returned the correct value. Therefore Windows does copy-on-write page remapping during a first SMC use, even though the application does not explicitly remap pages. [Microsoft's `VirtualQuery` documentation](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualquery) describes the image-page copy-on-write transition and its reporting limits.

The same-commit, pinned [control hunt #9](https://github.com/GregoryMorse/selfspectre/actions/runs/39160281020) failed in 4/60 jobs (five MODEXP32 first-result mismatches); 34 jobs reported virtualized AMD EPYC 7763 and all four failures were on that model. The pinned [preprivate hunt #10](https://github.com/GregoryMorse/selfspectre/actions/runs/39160318195) failed in 6/60 jobs; 41 reported EPYC 7763 and all six failures were on that model. In a failing Win32 replay, the harness had already materialized all 3,780 assembled-code pages before MODEXP32 returned a wrong first result; in a failing x64 job, it had materialized all 3,767 pages before a `SHR32` mismatch. Thus the first-write image-page transition is **not necessary** for these failures and pre-materialization is not a remedy. The 45 jobs on other reported CPU models across these two runs passed, but host model is correlated with other hypervisor details, so this is an affected runner class rather than proof of an AMD silicon defect or a Windows-only rule.

The x64 `SHR32` mismatch returned `0x0002A274` for expected `0x0001513A`, exactly twice the expected value, while the harness was stepping through successive shift counts for one input. This is consistent with a prior shift setting but does not prove it: that harness version did not print the operand, shift count, or patched instruction byte. Commit `5dc4a47` adds those diagnostics on failure. The linked x64 report listed ten crossing fields, none named in the direct `SHR32`/`SHL`/`SHR`/`XOR` path, but `patch_alignment.py` resolves only literal patch expressions in the source, not every macro-expanded store. Cache-line crossing therefore remains an untested hypothesis for some paths, not an established cause.

The [pinned telemetry hunt #11](https://github.com/GregoryMorse/selfspectre/actions/runs/39161931493) failed in 11/60 jobs: 11/36 jobs reporting virtualized EPYC 7763 failed, while 0/24 jobs reporting other CPU models failed. First-result errors appeared in `MUL32`, `DIV32`, and `MODEXP32`, sometimes together in one job; the focused MODEXP32 repeats were correct. No new `SHR32` failure appeared in this hunt. The new `edge_vectors shr32` mode isolates that primitive in the next hosted hunt.

The expanded-listing audit on the current local linked images resolved 481,117 x86 and 479,824 x64 assembled code-store instructions into 956 and 949 distinct patch fields. It found 15 x86 and 10 x64 fields crossing 64-byte boundaries. The x86 `shlres6+6` field used by the shift path crosses, but **none of the x64 `SHR32`/`SHL`/`SHR`/`XOR` patch fields crosses** in this link. The tool rejects an older listing whose object anchor shifted. This narrows the split-patch hypothesis for the observed x64 `SHR32` mismatch; it does not prove which patched byte was executed.

The [direct SHR32 hunt #12](https://github.com/GregoryMorse/selfspectre/actions/runs/39162890255) caught an x64 failure at shift 0: input `0xb7204374` returned `0x016e4086`, **exactly input shifted right by 7**, then two same-input calls returned the unshifted value. The entry instruction's patched count byte read back as 0 after the bad call, and the guest logical CPU stayed 0. The preceding test call had shift 31, whose low three bits are 7. This is evidence of stale shift state along the self-modifying path, but the entry-byte read alone cannot tell whether an intermediate patch was left at 7 or a later instruction executed stale bytes. The next diagnostic reads the split and lane fields immediately after a mismatch. It exports those x64 symbols without changing executable bytes; local before/after `.text` section hashes match for both architectures.

[AMD's Milan revision guide](https://www.amd.com/content/dam/amd/en/documents/processor-tech-docs/revision-guides/56683.pdf) lists erratum 1193, which can miss SMC detection after a specific page-frame remapping *without* the required invalidation. Ordinary Windows copy-on-write must still perform the required translation synchronization; the local probe does not establish that the erratum's invalidation condition occurs, and the failures after pre-materialization do not require that transition. The guide's other instruction-cache errata describe hangs rather than wrong return values.

On the local Debug|Win32 MSBuild image, `cdb` with the matching PDB disassembled `WriteExecMODEXP32_C`: it loads three 32-bit stack arguments, writes all twelve operand bytes, patches four result destinations and the return jump, then jumps to `WriteExecMODEXP32`. Its `modexpres3+2` destination patch starts at cache-line offset 63. In the separate linked CMake Release|Win32 vector image, `patch_alignment.py` finds different hot crossings: `modexp32arg3_1+2` at offset 63, `divretval2+2` at 62, and `shr32arg1_3+2` at 62. The links differ, so padding one location does not remove the others or establish a cause. The wrapper disassembly cannot establish correctness of the internal `MODEXP32`/`DIV32` trace or diagnose the earlier CI value without its operands. A focused 1,000-call differential run on each local assembled architecture and a subsequent 100-call mixed-operation run on each passed with no mismatch; the Windows CMake focus test passed 100 fresh triples and the legacy Debug|Win32 harness passed once. These are negative samples, not closure of the rare event.

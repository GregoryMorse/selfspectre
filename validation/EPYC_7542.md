# Bare-metal EPYC 7542 cross-host check

Recorded 2026-10-19 on a two-socket Gigabyte R282-Z93-00 with AMD EPYC 7542
(Rome, family 17h/model 49/stepping 0), BIOS R16 dated 2020-07-08, and
microcode `0x830107c`. The host ran Linux
`5.14.0-687.36.1.el9_8.x86_64`. CPU 0 and CPU 64 are SMT siblings; CPU 1 is
a different core on the same socket. This is a different CPU generation and
board from the failing bare-metal EPYC 7513 in [EPYC_7513.md](EPYC_7513.md).

The exact tracked source snapshot was commit `af845968128146b2160b567ce9a03eb55e2e6bf2`.
It was built with GCC 11.5.0 and the repository's pinned UASM 2.57, one build
or test at a time under `systemd-run --user --scope -p MemoryMax=1500M`.
The native CTest suite passed all four cases: `code_vectors`, `ref_soak_quick`,
`edge_vectors`, and `writeexec_harness`.

The full linked `we_xor_branchless` diagnostic (SHA-256
`fa31db13da2daf9dfbc8a8a48d481252f5928be253a5ff7214faf72cabf0c7a7`)
ran on CPU 0 with `yes` load pinned successively to CPU 1, 64, 64, and 1.
Each 40-million-call run returned zero wrong bytes: **0/160 million**.

For a direct cross-host comparison, the two-byte matched reduced images from
the EPYC 7513 investigation were copied unchanged and their SHA-256 hashes
verified (`b1fa7ae6...e1049cd` for NOP,
`234e6f8b...a823c7` for CPUID). Their executed assembly layout is identical
to the previously failing EPYC 7513 images. The NOP image returned zero wrong
bytes in four 40-million-call runs with the same CPU 1/64/64/1 load order;
the CPUID image returned zero in two 40-million-call runs with CPU 64 load.
Thus NOP was **0/160 million** and CPUID was **0/80 million** on this Rome host.
The `.78` result cannot discriminate the two variants or explain the Zen 3
failure. Zero observed errors are a negative sample, not a reliability proof.

With CPU 0 selected and automatic cache calibration, the native speculative
AES demo reported 9/10 correct and confident ten-round AES-NI trials and
10/10 one-round AES-NI trials; the corresponding C implementations reported
0/10. The RSA depth sweep reported 10/10 correct and confident at depths 1,
2, 4, 5, 6, and 8 in each available C and assembly case. These are measured
demo outcomes, not architecture-wide guarantees.

The BIOS on this host predates the one on the failing EPYC 7513 host, yet the
tested anomaly did not appear here. That rules out a simple claim that an old
BIOS alone is sufficient to reproduce it. A BIOS or microcode update on the
EPYC 7513 is still a useful controlled experiment, but neither that update
nor the firmware state of the virtualized GitHub EPYC 7763 hosts has been
verified as the cause. No assembly workaround was added from this result.
